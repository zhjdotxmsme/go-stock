AI 智能体交互重构

话题：把 /agent 页与侧边「AI 助手」浮窗合并到一套实现，修掉 A–E 五项交互缺陷
日期：2026-09-10  ·  分支：feat/multi-agent-analysis  ·  状态：待用户评审

1. 问题与实测证据

用户诉求（A–E 全选）：优化 /agent（菜单「AI 能力 → Ai智能体」）的交互。以下每条都是**读源码 + 在真实构建产物上实测**得到的，不是主观感受。

编号问题证据
A 流式期间输入框被禁用，且「发送」照常显示却点了没反应 TDesign @tdesign-vue-next/chat@0.4.5 内部：showStopBtn = loading || stopDisabled， 而 textarea 的 disabled = disabled || showStopBtn。页面传 :stop-disabled="isStreamLoad" → 整个流式过程 textarea 被 disable。同时自定义 #suffix 的「发送」按钮不受该开关影响照常渲染， 而 inputEnter() 开头 if (isStreamLoad.value) return; 直接静默返回； 输入为空时 if (!inputValue.value) return; 同样静默。
B 停止按钮点了停不下来，停止后内容还在悄悄追加 agent-chat.vue 的 onStop() 只清本地格式化计时器；fetchCancel.value 代码里从未赋值，永远是 null，后端 AgentHandler.AbortChatWithAgent() 从未被调用。 后端流继续，后续 agent-message 仍会往 chatList[0] 追加，而 UI 已显示"未在流式"。
C 看不见「在干什么」 t-chat-reasoning 是个 Collapse，页面只塞了 <t-chat-loading v-if="isStreamLoad"> 与 <t-chat-content> 到默认插槽，没有给 #header（折叠头为空）， 且 isStreamLoad 是全局标志（不是按消息索引）→ 思考中/思维链都藏在默认折叠的面板里。
D 执行步骤 / 思维链 / 分析报告 三块硬堆在一个气泡里 agent-chat.vue 的 #content 插槽把三块依次渲染，无分区标题、无折叠层次。
E 没有会话与上下文 chatWithAgent(...) 调用处只传了 7 个参数，sessionID 缺失（后端签名要求第 8 个）→ 记忆无法按会话隔离； 无历史列表、切页面即丢；模型/模式每次重选。

附加缺陷 1跨组件事件泄漏（已核实 Wails 源码）

agent-chat.vue 的 onBeforeUnmount 调用 EventsOff("agent-message")。 Wails v2.13 的实现是 unRegisterListener(name) { delete(e.listeners, eventName) } —— 按事件名一次清空所有监听者，不是只注销自己。

而 FloatingAgentAssistant.vue 挂在 app 根、永不卸载，也监听同名事件。 结果：只要打开过 /agent 页再离开，侧边 AI 助手的流式回复就彻底收不到，直到重启应用。 useAgentStream 在 onBeforeUnmount 里也有同样的 EventsOff。

附加缺陷 2持久化模型缺字段 → 恢复会话会丢数据

前端保存的消息带 steps（执行步骤）与 jsonMarkdown（分析报告）， 但后端 models.AiAssistantMessage 结构体只有 Role / Content / Reasoning / Time / ModelName / ToolCalls / ToolResults / Timeline —— 没有这两个字段，序列化时被丢弃。恢复历史后「执行步骤」「分析报告」全部消失。

附加缺陷 3新装环境缺少建表

ai_assistant_sessions 表不在任何 AutoMigrate 列表里 （backend/db/chat_memory.go 只迁移 ChatMemory / StockChangeHistory / MarketStatistic）。 现有两个库里有这张表，是历史版本留下的。全新安装的机器上保存会失败，而前端 saveHistory() 的 .catch(() => {}) 会静默吞掉。

2. 现状盘点：两套实现，能力不对等

/agent 页是遗留实现（TDesign t-chat，809 行内联逻辑）；侧边浮窗 + components/agent/* 是重构后的实现。用户需要的能力后端全都有，浮窗也基本都用了，是 /agent 页没用。

能力后端侧边浮窗/agent 页
真中断✅ AbortChatWithAgent()✅ 并带 isAborted 守卫❌ 只停本地计时器
会话隔离✅ ChatWithAgent(..., sessionID)✅ 传了 sessionId❌ 参数缺失
会话持久化✅ ai_assistant_sessions 表 + upsert✅ 保存/恢复已接线❌ 无
步骤/思维链/报告分区—✅ 有标题与计数、自动展开❌ 折叠头为空
流式中继续输入—❌ :disabled="isStreamLoad"❌ 更糟（组件内部锁死）
会话列表❌ 无 List 接口❌ 单会话❌ 无

3. 方案（已选：方案 1）

抽一个共享面板 AgentChatPanel.vue + 一个 pinia store 作为会话唯一真源，/agent 页与侧边浮窗共用。

  • A 在共享层修一次 → 两个入口同时生效
  • B/C/D/E 直接继承浮窗已验证的实现，不重写
  • 彻底摆脱 TDesign t-chat 的 showStopBtn 语义坑

已否决：方案 2（只重写 /agent 页 → 逻辑仍两份，以后每个 bug 修两遍）；方案 3（继续给 TDesign 打补丁 → 与组件内部行为对着干，长期最贵，正是当前"怪"的来源）。

4. 架构与组件边界

stores/agent.ts                        ← 会话唯一真源（pinia）
   ├─ state : messages / sessionId / sessions / isStreamLoad / isAborted
   │          aiConfigId / sysPromptId / userPromptId
   │          thinkingMode / memoryMode / memoryCount / agentMode
   ├─ action: sendMessage / abortStream / startNewChat
   │          loadHistory / loadSessions / switchSession / deleteSession / saveHistory
   └─ 订阅  : agent-message（全局仅注册一次，永不 EventsOff）  ← 修跨组件泄漏

components/agent/AgentChatPanel.vue    ← 共享面板（新增）
   └─ 提示条 + 消息列表(MessageBubble) + AgentChatFooter
      props: density('panel' | 'page')

components/agent/AgentSessionList.vue  ← 会话侧栏（新增，仅页面模式）
components/agent/AgentChatFooter.vue   ← 沿用 + 修 A
components/agent/MessageBubble.vue     ← 沿用 + 当前步骤摘要 + 「已中断」标记
components/agent/useShareExport.js     ← 保留 composable（依赖 DOM 截图，各宿主自持）

components/agent-chat.vue              ← 重写：会话侧栏 + AgentChatPanel（全宽）
components/FloatingAgentAssistant.vue  ← 瘦身：抽屉壳 + 同一个 AgentChatPanel

边界原则：面板不知道自己跑在页面还是抽屉里（靠 density）；store 不知道 UI 长什么样；两个宿主只调 store 的公开动作。

store 与既有 composable 的关系

把 useAgentStream 的流式与会话逻辑移入 store（改为 store 内部模块），因为事件订阅必须是全局单例；useMessageGroups 的展开状态、useAgentOptions 的选项加载同样上移。仅 useShareExport 保留为 composable（它绑定具体 DOM 节点做截图导出，两个宿主各持一份是合理的）。

5. 数据流

【发送】用户输入 → store.sendMessage() ├─ 若 isStreamLoad → 先 abortStream()（= 中断并发送） ├─ 追加 user 消息 + 空 assistant 占位（steps:[]） ├─ 清空输入框 → saveHistory() → ensureLatestGroupExpanded() └─ chatWithAgent(text, aiConfigId, sysPromptId, memoryMode, memoryCount, thinkingMode, agentMode, sessionId) ← sessionId 必须非空 【流式】后端 agent-message → store.onAgentMessage() ├─ isAborted === true → 直接丢弃（修 B 的"迟到内容追加"） ├─ reasoning_content 以 [STEP] 开头 → parseStepText() → push 到 steps ├─ 其余 reasoning_content → 累加 rawReasoning ├─ content === 'agent-DONE' 或 response_meta.finish_reason === 'stop' │ → isStreamLoad=false、格式化收尾、saveHistory() └─ 其他 chunk → 累加 rawContent（正文）
【中断】用户点「中断」/ 在有草稿时点「中断并发送」 ├─ isAborted = true、isStreamLoad = false、停格式化计时器 ├─ 给该条 assistant 消息打 aborted = true（气泡显示「已中断」） └─ systemApi.abortChatWithAgent() ← 真正 cancel 后端 context 【会话】面板挂载 → loadSessions() → loadHistory(sessionId) ├─ sessionId 空 → 取最新一条（沿用 getAiAssistantSession('') 语义） ├─ 新建 → sessionId = Date.now().toString() └─ 删除 → deleteAiAssistantSession(id) → 重新 loadSessions()

6.1 两处需要定死的细节

  • density 的确切差异（避免"默认展开更多"这种含糊说法）：
    行为page（/agent 页）panel（侧边浮窗）
    消息区顶部「当前步骤」摘要行显示显示
    执行步骤分区默认展开默认折叠，只显示标题 + 计数
    思维链分区默认展开默认折叠
    分析报告(jsonMarkdown)分区默认展开默认折叠
    用户提问折叠头默认展开默认折叠
  • 模型/模式记忆的落点：存 localStorage，键 agent.prefs，值 { aiConfigId, sysPromptId, userPromptId, thinkingMode, memoryMode, memoryCount, agentMode }。 读写由 stores/agent.ts 负责（初始化时读、变更时写）。不动后端 settings 表，避免与「设置」页耦合。
  • 「已中断」标记不持久化：aborted 仅是本次会话的 UI 状态，saveHistory() 不写入该字段； 从历史恢复的消息不会显示「已中断」（已中断的残缺回答本身已保存在 content 里）。

8. 错误处理

callApi 是"不抛异常、返回 {data, error}"的封装 —— 现有代码大量只取 data，所以失败时完全静默，这正是"点了没反应"的根源。

场景要求
空输入 / 未选模型message.warning，不静默返回
后端返回 error（含 data === null）store 内统一检查并 message.error（带可读文案）
保存会话失败不再 .catch(() => {})；降级为顶部提示"本次会话未能保存"
流式无响应看门狗：120 秒内未收到任何 chunk 即判定超时 → message.error('AI 无响应，请重试') 并解除流式态（自动展开/折叠逻辑复用 stores/app.ts 已有写法）
中断后迟到事件isAborted 守卫丢弃（已有），不追加、不改状态

9.3 UI 交互回归（把这次的探针固化）

本轮排查用 chromedp（已是项目依赖）起了静态服务 + stub 掉 window.go / window.runtime + 加载真实构建产物， 能精确断言 DOM 状态。建议固化为 cmd/uitest（默认不参与 go test ./...，显式运行）：

  • 流式中 textarea 未 disabled、主按钮文案为「中断并发送」

  • 刷新后会话与模型/模式被恢复
  • 会话列表：新建 → 出现在列表；删除 → 从列表消失

取舍：会把一个 cmd/uitest 工具包纳入仓库（复用既有 chromedp 依赖）。若不希望入库，可只保留 9.1/9.2，UI 部分改由人工验收。
